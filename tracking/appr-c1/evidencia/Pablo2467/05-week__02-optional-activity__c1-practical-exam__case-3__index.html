Framework y SPA

Componente, Estado, Enrutamiento y por qué una SPA necesita una API

¿Qué es un componente?

Un componente es una pieza de interfaz reutilizable y autocontenida que combina estructura (qué se muestra), lógica (cómo se comporta) y, opcionalmente, sus propios estilos. Un componente se puede reutilizar varias veces con distintos datos de entrada (props), sin duplicar código. 

// Pseudocódigo de un componente "TarjetaProducto"
componente TarjetaProducto(props) {
  retornar:
    contenedor {
      titulo: props.nombre
      texto: props.descripcion
      texto: "$" + props.precio
    }
}

// Uso del componente con distintos datos
TarjetaProducto({ nombre: "Producto 1", descripcion: "...", precio: 10000 })
TarjetaProducto({ nombre: "Producto 2", descripcion: "...", precio: 20000 })

¿Qué es el estado?

El estado (state) es la información interna de un componente que puede cambiar con el tiempo (por ejemplo, tras una interacción del usuario o una respuesta de una API) y que, al cambiar, hace que el componente se vuelva a renderizar automáticamente para reflejar ese cambio en la pantalla. 

// Pseudocódigo de un componente con estado
componente ContadorClicks {
  estado contador = 0

  al hacer click en boton:
    contador = contador + 1

  retornar:
    contenedor {
      texto: "Has hecho click " + contador + " veces"
      boton: "Sumar"
    }
}
// Cada vez que "contador" cambia, la vista se actualiza sola

¿Qué hace el enrutamiento?

El enrutamiento (routing) es el mecanismo que decide qué componente mostrar según la URL actual, sin recargar la página completa. En una SPA, el "router" del framework intercepta los cambios de URL y renderiza dinámicamente el componente correspondiente en el mismo documento HTML. 

// Pseudocódigo de enrutamiento
rutas = {
  "/"          : ComponentePagina de Inicio,
  "/productos" : ComponenteListaProductos,
  "/usuarios"  : ComponenteListaUsuarios
}

al cambiar la URL:
  componente_a_mostrar = rutas[url_actual]
  renderizar(componente_a_mostrar)
  // no se recarga el navegador, solo cambia el contenido

¿Por qué una SPA necesita una API?

Una SPA (Single Page Application) carga un único documento HTML inicial y luego todo el contenido dinámico se genera con JavaScript en el navegador. Como esa página no se recarga para navegar entre secciones, tampoco recibe HTML nuevo del servidor en cada "vista" (a diferencia de una app tradicional). Por eso, para mostrar datos reales y actualizados (usuarios, productos, mensajes, etc.), la SPA necesita pedirlos por su cuenta, generalmente vía JavaScript con fetch, a una API que le devuelva esos datos (normalmente en formato JSON), como hicimos en el Problema 2 de este examen. La API se convierte así en la única fuente de datos "frescos" de la aplicación, ya que el HTML por sí solo quedó estático desde la primera carga.

SPA vs MPA English requirement

A Single Page Application (SPA) loads a single HTML page and updates the content dynamically with JavaScript as the user navigates, without reloading the whole page. A Multi Page Application (MPA), on the other hand, loads a new HTML page from the server every time the user navigates to a different section, which usually means slower transitions but simpler, more traditional server-side rendering.
